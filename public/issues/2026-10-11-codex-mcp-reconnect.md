# Codex MCP 두 개 재연결 — 여러 번의 재시도 끝에 성공

- **발생 일자:** 2026-10-11 (최초 장애 발생 시각은 미확인)
- **해결 일자:** 2026-10-11 15:16 KST (볼칸의 현재 대화에서 도구 호출 성공)
- **심각도:** medium
- **재발 가능성:** medium
- **영향 범위:** 볼칸 Codex CLI의 `computer-use`·`codex_app`. 아테나에서도 같은 문제를 처리했다는 사용자 보고가 있었다. 이 글의 복구 검증은 볼칸 기준이다.

## 증상

시작은 “연결되지 않은 MCP 두 개를 다시 연결해 달라”는 요청이었다. 터미널에서 `computer-use`와 `codex_app`이 비활성 상태로 보였다. 설정을 손본 뒤에도 별도 연결 시험의 성공과 현재 터미널의 상태가 일치하지 않았다. 두 개를 켜는 작업이 여러 번의 진단과 재시도로 이어졌다.

사용자는 볼칸과 아테나의 Codex가 이 문제를 처리하면서 **주간 사용량 약 5%를 쓴 것 같다**고 말했다. 이는 사용자 체감 추정이다. 작업별 정확한 토큰 사용량은 측정하지 못했다.

## 원인

1. **computer-use의 기존 비활성 설정.** 사용자 설정에 남은 `enabled=false` 항목이 정상 플러그인 연결을 막고 있었다. 오래된 상대 경로도 이 항목에 함께 들어 있었다.
2. **codex_app의 비활성 설정과 실행 경로 인증 실패.** 서버를 켜고 앱 연결 경로를 전달해도 기존 Node 실행 경로는 데스크톱 앱의 서명 검사를 통과하지 못했다. 앱 로그에는 `dynamic_app_tools_peer_rejected reason=missing-code-signing-identity`가 남았다.
3. **설정 변경과 현재 세션 반영을 혼동하기 쉬운 상태.** 새 진단 프로세스가 도구 목록을 받아도 이미 실행 중인 CLI에 같은 연결이 반영됐다는 뜻은 아니었다.

비활성 설정이 처음 들어간 시점과 경위는 확인하지 못했다.

## 조치

- 첫 단계에서 `computer-use`의 비활성 설정을 제거했다. 연결 시험에서 도구 10개를 받았다. `codex_app`은 기존 실행 경로에서 계속 거부됐다.
- 실행 경로를 비교한 뒤, OpenAI가 서명한 Node로 기존 Codex CLI 0.162.1을 실행하도록 로컬 실행기를 구성했다. 실행할 때 현재 데스크톱 앱의 연결 경로를 전달하게 했다. 앱의 서명 검사는 유지했다.
- 새 기본 CLI로 `codex_app` 도구 38개와 `computer-use` 도구 10개의 연결을 확인했다.
- 같은 대화와 GPT-6-Astra max 설정을 유지해 볼칸 Codex CLI를 한 번 재시작했다. 첫 재시작 대기는 작업 종결 검사에 걸려 시간 초과로 취소됐다. 기록 상태를 맞춘 뒤 다시 시도해 재시작했다.
- 15:16 KST에 현재 대화에서 두 MCP의 읽기 전용 도구 호출이 모두 성공했다. 이후 사용자가 보낸 스크린샷에서도 두 항목의 `connected` 표시를 확인했다.

MCP 연결과 앱별 조작 허용은 별개였다. 연결 후에도 Ghostty 화면 캡처는 컴퓨터유즈의 안전 제한으로 차단됐다. 화면 확인은 사용자가 보낸 스크린샷으로 마쳤다.

## 놓친 승인 경계

볼칸은 “연결해주세요”를 CLI 재시작까지 포함한 승인으로 해석했다. 별도의 재시작 승인은 받지 않았다. 사용자는 아테나는 재시작 승인을 받았다고 지적했다.

대화와 모델을 보존해도 재시작 승인 확인을 대신할 수는 없다. 볼칸은 승인 범위를 넓게 해석한 점을 인정했다. 재시작 승인이 명확하지 않으면 대상과 영향을 먼저 확인해야 한다.

## 예방 (Forcing function 우선)

- **막을 코드/훅:** 로컬 실행기 `~/bin/codex`, `~/.codex/launch-signed-cli.mjs`.
  - 기존 Codex를 서명된 런타임으로 실행한다. 시작할 때 현재 앱 연결 경로를 찾는다.
  - 이 실행기의 적용 결과는 현재 세션의 실제 도구 호출로 확인했다. 자동 복구 감시나 새 승인 훅을 설치한 것은 아니다.
- 다시 실패하면 비활성 설정, 실행 경로 인증, 현재 세션 반영 여부를 차례로 구분한다. 같은 실패를 근거 없이 반복하지 않는다.
- 완료 기준은 현재 대화의 실제 도구 호출과 터미널 연결 표시다. 별도 진단 성공만으로 현재 세션까지 완료됐다고 보고하지 않는다.

## 픽업
- **신뢰의 출발점은 실제 실행 검증이다.** 에이전트가 앱을 실행하고 사용자 동작을 재현하며 트레이스·힙 스냅샷을 수집하도록 만든다. 사람이 매번 화면과 오류를 전달해야 한다면 사람이 검증 병목으로 남는다. 동작의 정확성과 코드의 품질은 구분해야 한다고 강조한다.
- **앱 조작 도구에는 기능 지도가 필요하다.** 기능별 진입 경로, 단축키, UI 요소와 선택자를 정리하면 에이전트가 막연한 버그 제보에서도 재현할 위치를 찾을 수 있다. 조작 API만 제공해서는 제품을 이해하지 못하므로 지도도 함께 유지한다.
- **스킬도 평가하고 반복 개선한다.** 실제 도구 호출과 실패 행동을 관찰해 스킬을 만들고, 기대 행동을 평가 기준으로 삼아 수정 전후를 확인한다. 다른 모델의 평가를 교차 확인에 활용하는 등 검증 도구 자체도 검증한다고 설명한다.
- **로컬에서 신뢰를 쌓은 뒤 자동화 범위를 넓힌다.** 먼저 눈앞에서 에이전트가 앱을 제대로 다루는지 확인하고, 이후 클라우드의 버그 재현과 PR 작업으로 확장한다. 한 에이전트도 믿기 어려운 단계에서 수백 개를 실행하면 토큰과 비용을 낭비할 수 있다고 경고한다.
- **가장 쉬운 구현 경로가 올바른 경로가 되게 설계한다.** 기능 코드를 한곳에 모으고 관례적인 진입점을 제공해 에이전트가 기존의 좋은 패턴을 복사하게 한다. Electron에서는 프로세스 간 의존성을 검사해 무거운 작업이 렌더러로 섞이는 문제를 막는 사례를 소개한다.
- **반복되는 리뷰 지적을 기계가 강제하는 규칙으로 바꾼다.** 아키텍처·정적 분석·린트·CI를 강한 제약으로 두고 문서 규칙과 스킬은 보완층으로 사용한다. 사람이 같은 위반을 계속 지적한다면 자동 검사나 구조 변경으로 그 문제를 제거할 수 있는지 묻는다.
- **변경 이력과 투자 비용까지 설계한다.** PR의 절대 줄 수보다 변경 의미가 독립적이고 되돌리기 쉬운지를 중시한다. 검증 환경과 구조 개선에 드는 초기 토큰 비용은 이후 팀 전체의 반복 작업 감소와 기여 범위 확대를 함께 놓고 평가해야 한다고 설명한다.

## 용어
- **검증 스킬** [하니스 · 패턴]: 에이전트가 실제 앱을 실행·조작하고 결과를 관찰하도록 절차와 도구를 묶은 스킬.
- **기능 지도(Feature Map)** [지식 · 컨텍스트 자산]: 제품 기능에 도달하는 경로와 UI 조작 정보를 정리한 문서.
- **평가(Eval)** [하니스 · 패턴]: 정해진 과제와 기준으로 에이전트나 스킬이 기대한 행동을 하는지 확인하는 과정.
- **힙 스냅샷** [도구 통신 (MCP · CLI · API)]: 특정 시점에 프로그램이 메모리에 보관한 객체와 참조 관계를 조사하기 위한 자료.
- **정적 분석** [하니스 · 패턴]: 프로그램을 실행하지 않고 코드의 규칙 위반이나 의존성 문제를 검사하는 방법.
- **CI** [워크플로우 · 문화]: 변경마다 빌드와 검사를 자동 실행해 통합 전에 문제를 발견하는 절차.
- **렌더러 프로세스** [기타]: Electron 앱에서 화면 표시와 사용자 인터페이스 실행을 담당하는 프로세스.

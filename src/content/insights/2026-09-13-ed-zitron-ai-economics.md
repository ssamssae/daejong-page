## 내 작업에 적용
아래는 인터뷰를 계기로 정리한 운영 제안이다. 발표자의 발언이나 이미 실행한 조치로 읽지 않는다.

### 1. 토큰 수보다 성공한 작업 한 건의 비용
호출비만 기록하면 실패한 시도와 사람이 다시 확인하는 시간이 빠진다. 작업마다 `도구 이용료 + 검토 시간의 비용 + 재작업 비용`을 합치고, 실제 완료 건수로 나눈다. 작은 수정이 여러 번 실패했다면 많이 생성한 것이 성과가 될 수 없다. 정액 요금과 종량 요금은 각각 실제 지출과 사용 한도를 기준으로 비교한다.

### 2. 가격이나 한도가 바뀌어도 끝낼 수 있는 작업
모델이 바뀌어도 읽을 수 있게 원본 자료, 변경 파일, 검사 결과, 다음 단계를 남긴다. 도구 교체가 곧 작업 소실이 되지 않도록 결과물을 일반 파일 형식으로 보관한다. 구독 하나를 해지해도 이어서 처리할 수 있는지를 운영 품질의 기준으로 삼는다.

### 3. 사람이 확인할 지점을 결과 가까이에 둔다
코드 생성은 실행 결과로, 데이터 이전은 이전·이후 데이터 보존으로, 게시 작업은 실제 게시 내용으로 판정한다. 테스트 개수가 많아도 사용자에게 필요한 마지막 동작을 확인하지 못했다면 미확인으로 남긴다. 검증은 모든 단계를 같은 강도로 검사하기보다 실패 피해가 큰 경계에 집중한다.

### 4. 반복 계산과 해석을 나눈다
파일 목록·해시 비교·정해진 형식 검사처럼 규칙이 명확한 일은 스크립트로 처리한다. 모호한 요구 해석이나 서로 충돌하는 근거 판단에 모델을 쓴다. 사람이 개입한 횟수와 예외 처리 시간을 함께 기록하면 ‘자동화했다’는 말의 실제 범위를 볼 수 있다.

### 5. 낙관과 비관 모두 다음 측정으로 바꾼다
먼저 작은 실제 작업을 정하고, 수동 작업과 같은 완료 기준으로 비교한다. 가격 상승, 모델 교체, 일시적 접근 불가 상황에서도 결과를 회수할 수 있는지 확인한다. 특정 연도의 붕괴를 전제로 운영을 멈추거나, 미래 성능 향상을 전제로 현재 손실을 무시하지 않는다.
